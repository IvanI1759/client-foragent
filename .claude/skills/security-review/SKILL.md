# Security Review — Telegram Bot (Node.js + Telegraf + Supabase + Gemini)

Полный аудит безопасности проекта перед деплоем. Основан на внутреннем чеклисте (`security_checklist.docx`) и адаптирован под стек: **Node.js + Telegraf, Supabase + pgvector, Google Gemini API, Render, RAG pipeline**.

---

## Как проводить аудит

1. Пройди каждый раздел чеклиста ниже
2. Для каждого пункта проверь код, конфиги, переменные окружения
3. Отмечай статус: `[x]` пройдено, `[ ]` не пройдено, `[~]` частично / не применимо
4. Заполни итоговую таблицу в конце
5. Вынеси вердикт: PASS / CONDITIONAL PASS / FAIL

---

## 1. Секреты и конфигурация

### 1.1 Базовое

- [ ] API-ключи (Gemini, Supabase, Telegram BOT_TOKEN) хранятся только в `.env` или Render Environment Variables — не в коде
- [ ] Секреты не попадают в логи (`console.log`, `console.error` не выводят ключи/токены)
- [ ] Файл `.env` указан в `.gitignore` и не залит в Git
- [ ] `.env.example` содержит только имена переменных без реальных значений
- [ ] Gemini API key доступен только через `process.env.GEMINI_API_KEY` (или аналогичную переменную)

### 1.2 Инфраструктура (Render + Supabase)

- [ ] Зависимости проверены: `npm audit` не показывает critical/high уязвимостей
- [ ] `package-lock.json` зафиксирован в репозитории
- [ ] Debug-режим выключен на проде (нет `DEBUG=*`, нет verbose-логирования)
- [ ] Supabase: используется `SUPABASE_SERVICE_ROLE_KEY` только на сервере, `SUPABASE_ANON_KEY` не даёт доступ к закрытым таблицам
- [ ] Supabase RLS (Row Level Security) включён на таблицах с данными пользователей
- [ ] Render: автодеплой не тянет секреты из публичных веток

## 2. Доступ и авторизация

### 2.1 Telegram-авторизация

- [ ] **Webhook защищён `secret_token`**: при настройке webhook передаётся `secret_token`, Telegraf проверяет заголовок `X-Telegram-Bot-Api-Secret-Token`
- [ ] **Валидация `user_id` только из контекста Telegraf** (`ctx.from.id`), а не из параметров запроса или callback_data
- [ ] Нельзя подменить `user_id` через параметры — бот берёт ID исключительно из объекта update, валидированного Telegram
- [ ] Webhook endpoint не отвечает на запросы без корректного `secret_token`
- [ ] Список разрешённых пользователей хранится в Supabase, проверка идёт по `user_id` из БД

### 2.2 Контроль доступа

- [ ] Неавторизованные пользователи получают отказ с сообщением, содержащим их `user_id` (чтобы администратор мог добавить)
- [ ] Нет IDOR: пользователь не может получить чужие документы/чаты через подмену ID
- [ ] Админ-функции (если есть) защищены отдельной проверкой роли, не просто скрыты

### 2.3 Rate Limiting

- [ ] **Пользовательский rate limit**: не более 20 запросов/час на пользователя (или настроенное значение)
- [ ] **Глобальный счётчик Gemini API**: отслеживается общее количество вызовов, есть лимит/алерт при приближении к квоте
- [ ] Rate limit корректно сообщает пользователю о превышении (не молчит и не падает)
- [ ] Rate limit данные хранятся в Supabase или in-memory с TTL — нет утечки памяти

## 3. Пользовательский ввод и RAG Pipeline

### 3.1 Текстовый ввод

- [ ] Весь текст от пользователя валидируется на сервере перед обработкой
- [ ] Нет возможности injection через текстовые сообщения (prompt injection в Gemini учтён: system prompt задаёт рамки)
- [ ] Длина сообщений ограничена (нет возможности отправить 1MB текста и повесить обработку)

### 3.2 Загрузка файлов для RAG

- [ ] **Проверка MIME-типа**: файл валидируется по magic bytes, а не только по расширению (допустимые: PDF, DOCX, TXT и др.)
- [ ] **Ограничение размера**: файлы больше 10MB отклоняются с понятным сообщением
- [ ] Файлы не сохраняются с пользовательским именем напрямую (sanitize имени файла или использование UUID)
- [ ] Временные файлы удаляются после обработки (нет накопления в `/tmp` или аналоге)
- [ ] Парсинг документов (PDF, DOCX) не уязвим к zip-bomb или XXE (если используется XML-парсер)

### 3.3 Embeddings и pgvector

- [ ] Чанки текста ограничены по размеру перед отправкой в Gemini Embedding API
- [ ] Документы общие по `agent_type` — доступ контролируется auth middleware (только авторизованные), загрузка только OWNER
- [ ] Нет SQL injection в запросах к pgvector (используются параметризованные запросы или Supabase client)

---

## 4. Хранение данных и транспорт

- [ ] HTTPS используется для всех соединений (Render по умолчанию, но проверить redirect с HTTP)
- [ ] Supabase подключение через SSL
- [ ] Персональные данные пользователей (сообщения, документы) не логируются в plain text
- [ ] Чувствительные данные не попадают в URL (query params)
- [ ] Данные в Supabase: нет таблиц с открытым доступом без RLS
- [ ] Пароли (если есть) хранятся хэшированно (bcrypt/argon2)

---

## 5. Telegram-специфика

- [ ] `BOT_TOKEN` не фигурирует в логах, ответах бота, error messages
- [ ] Webhook URL содержит случайный компонент или защищён `secret_token` (не просто `/webhook`)
- [ ] Бот корректно обрабатывает невалидные update (не падает, не раскрывает stack trace)
- [ ] Бот не отвечает в группах, если не предназначен для этого (или ответы ограничены)
- [ ] Inline-клавиатура: callback_data валидируется, нет возможности подставить произвольные данные

---

## 6. Gemini API

- [ ] API key передаётся только через переменную окружения, не хардкодом
- [ ] Ответы от Gemini обрабатываются: проверяется наличие content, обрабатываются ошибки (quota exceeded, invalid request)
- [ ] Safety settings настроены — бот не ретранслирует потенциально опасный контент без фильтрации
- [ ] Prompt injection mitigation: system prompt содержит инструкции игнорировать попытки переопределения роли
- [ ] Таймаут на запросы к Gemini API установлен (бот не зависает при медленном ответе)
- [ ] Глобальный счётчик вызовов Gemini API с алертом/блокировкой при достижении лимита

---

## 7. Деплой и мониторинг (Render)

- [ ] Health check endpoint настроен (Render может пинговать бота)
- [ ] Graceful shutdown: бот корректно завершает работу при перезапуске Render
- [ ] Логирование: ошибки пишутся в Render Logs, но без секретов и PII
- [ ] Переменные окружения заданы в Render Dashboard, не в коде
- [ ] Автодеплой настроен только из защищённой ветки (main/master)

### Примеры классификации

**:red_circle: Критично:**
- API-ключ Gemini или BOT_TOKEN в коде / в Git
- Webhook без `secret_token`
- `user_id` берётся из параметров запроса, а не из Telegram update
- SQL injection в запросах к Supabase
- RLS выключен на таблицах с пользовательскими данными

**:yellow_circle: Важно:**
- Нет rate limiting (пользовательского или глобального Gemini)
- Файлы не проверяются по MIME-типу / нет лимита размера
- Нет таймаута на Gemini API запросы
- Ошибки раскрывают stack trace пользователю
- `npm audit` показывает high-severity уязвимости

**:green_circle: Рекомендации:**
- Добавить health check endpoint
- Настроить алерты на превышение квоты Gemini
- Улучшить сообщение об отказе в доступе (показывать `user_id`)
- Добавить graceful shutdown
- Логировать аномальную активность (слишком частые запросы)
